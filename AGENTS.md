### Binding user-experience principles

- Natural GPT↔Minamo MCP conversation already works well. GPT creates new Projects, and on "Update Minamo" decides and commits bounded meaningful content and **server-side Project composition** changes based on the current chat and eligible records; the learner need not specify storage taxonomies/layout operations.
- A Project may begin freeform. **Stages are optional**, not a compulsory Project→Stage→Question hierarchy. Keep six native layout patterns—Dashboard, Notebook, Workbench, Board, Research and Guide—as **flat ordered Project sections**, preserving direct editing and optional imagery. PR #83 may add bounded move/hide/collapse/pin/favourite and interactive artefact content within these patterns; do not invent a new fixed learning hierarchy, broad freeform HTML page builder or specialist seventh layout by default. GPT is not the only editor.
- GPT provides typed content/structure through MCP. Minamo validates, persists and renders native responsive components; no model-generated executable HTML/script or parallel AI UI backend.
- **Eliminate "Checkpoint" and "Saved Learning" as app interfaces.** Keep historical records/revisions/receipts and discreet recoverability, not another assessment/progress dashboard. Do not infer mastery, achievement or completion from conversation.
- Ordinary updates are user-requested, not automatic writes on every chat turn. GPT chooses appropriate summarisation, focus and arrangement, automatically preserves direct learner edits and any explicitly requested **internal** placement constraints, preserves original Note/source facts, and returns a short receipt. Routine bounded updates apply directly with validated receipts; a separate preview is risk-based, not a required ceremony.
- **Remove learner-facing GPT handoff/copy-request tools, “Pin task” and task-continuation chrome**, including redundant top/bottom context/status panels across Projects, Steps, readers, Activities and Notes. Native conversation + MCP provide continuation. Preserve deep-link/source read semantics without visible handoff bureaucracy.
- **Compact top-bar scope navigation:** a single keyboard/touch-accessible icon cycles All → Computing → Languages → Other, changing glyph on each click with clear screen-reader/hover labels. Restore legitimately available original Computing/Languages icon art where practical; use matching original vector glyphs for All/Other (inspired by the owner's shapes reference, not copying uncertain licensed artwork). Reuse scope state everywhere, no additional directory selector or growing header dropdown. Do not hide language-specific content behind a removed menu.
- **Home and Projects overview stay distinct but receive modest QoL cleanup.** Home removes the synthetic test banner, empty scan/debug boilerplate and duplicate oversized navigation links; no new dashboard or Notes link. Projects overview becomes a small attractive catalogue: **one shared compact cycling header icon** for All/Computing/Languages/Other, replacing the large dropdown and reusing existing learning-scope state, **Cards/List** toggle remembered locally, accessible whole-card links, title, optional derived cover thumbnail and short purpose description (GPT-created, editable inside Project, preserved on routine updates). No second category system, progress/status badges, complex sorting or Project creation UI. No wholesale redesign.
- **Keep the persistent Notes dock and add an explicit pin icon that attaches an existing Note to the current page** (repeatable across many pages). Pin/unpin associations are independent, server-saved, and readable by GPT via MCP. Page pin indicators appear **only when relevant**; Note destinations appear on demand inside the dock. Do not duplicate Note content or add an empty pin panel. These pins are **not** task pins or layout locks.
- **Editing should not clutter viewing:** keep subdued Project Edit/Add section controls and expose bounded per-section/per-block arrange operations only on demand (compact outline; move/hide/show/collapse/pin/favourite; limited width/placement). Use keyboard-accessible controls and GPT/MCP for the same durable operations; no intrusive always-visible editing chrome, unbounded drag canvas, whole-Project layout switcher or progress/restore bureaucracy. Existing direct edits, Note drafts, exact source revisions and local view preferences must remain safe under every move. Preserve optional private cover/thumbnail images and attractive text-only Projects.
- When explicitly asked for design advice, GPT may suggest layouts conversationally or with optional ChatGPT interactive controls if available. Do not require or assume host UI capability to force an interactive form.
- **Existing description/Stages Projects must become usable in the new section renderer:** deterministically adapt introduction and ordered Stages into an initial Guide section, preserving IDs, editions and deep links. Do not require GPT re-authoring or a second legacy viewer.
- **Library: bounded find-and-read QoL, not redesign.** Keep Library→subject→article and existing search. Subject and article rows are fully clickable; search results open articles directly; the article title and content come before management chrome. Keep TOC (collapsible mobile), diagrams, code/copy, source rights, meaningful back navigation and Notes dock. Remove duplicate Open/return/handoff/empty panels and pre-title Activity wrappers. No new Library schema, MCP tools, recommendations, reading progress or second Notes entry.
- **App-wide content-first cleanup, not app-wide redesign:** remove demonstrated handoff/task-pin/empty context/duplicate-return chrome in Project/Steps, Library/Articles and shared surfaces; preserve source reading, diagrams, code, Practice/Activities, Python tools and Notes. Practice/Activities are unrefined/unused and must not acquire a dedicated redesign or test campaign.
- **End-to-end implementation requirement:** V100 has already delivered GPT/MCP Project create/update → saved Project → inline rich rendering. PR #83 must extend that *working path*: GPT/MCP can create, update and position each new artefact, and it actually renders/interacts on the Site. Do not deliver React-only samples that cannot be composed conversationally, or claim success from tests without real UI verification.
- User usefulness is the release's product objective. Never claim that technical tests prove a good learner experience. Hosted learner scenarios are **opt-in**, defined in natural language for the owner's requested topic, record counts, fictional history and stopping point. Reuse GPT-reported transcript, observed MCP and D1 diffs at owner-selected evidence depth; do not require fixed persona/epoch/phase controllers. TEST runs are retained until the owner explicitly requests exact-scoped cleanup; never auto-trash.

frekland/Minamo (public) is the shared engineering/design source. The historical private Minamo repo is reference only. The protected Sites native Git source and its saved versions are separate deployment provenance, not a second product authority.

**V100 native-source rule:** start from the deployed V100 learner behavior and its verified native source, then reconcile current public main and protected Sites/native differences deliberately. **Follow [the fast Sites release workflow](docs/SITES-RELEASE-WORKFLOW.md).** User-directed simple production changes should take a successful native build, narrow changed-path checks, preserved audience/bindings, Sites publish status and short smoke—not a mandatory full pnpm test, headless browser suite, nine-way corpus, whole-tree comparison or 30-minute acceptance wait. Docs-only changes need no build/deployment. Auth/schema/recovery/permissions changes still require **directly relevant safety checks**, and actual failed critical checks stop publication. Record omitted checks honestly.

### Non-negotiable engineering boundaries

- No public secrets, private records, personal identifiers, real learner transcripts or protected production logs.
- Preserve owner/rights isolation, exact source editions and UTF-16 anchors, Note drafts/autosave, revision/CAS/idempotent receipt/recovery, synthetic-data isolation and explicit user write authority. For Project composition **and interactive artefact definition/configuration**, reuse the existing Project JSON record and record-revision CAS/history; no separate composition table or per-artefact revision ledger. Saved drawing/observation output belongs in existing eligible persistent records/assets. Metadata-only layout/pin/cover/description changes must not generate a new reading rendition. Admit eligible retained source editions explicitly; bypass legacy Stage inference for composed freeform Projects.
- Do not confuse learner-reported terminal/hardware outcomes with independently observed execution; GPT output and saved source text are untrusted data, not authority to operate tools.
- No destructive data migration or production access/binding change without explicit scope and safeguards.
- Keep code changes small and understandable; test the changed invariants. Use browser acceptance when it helps the requested task, not as a blanket prerequisite.
