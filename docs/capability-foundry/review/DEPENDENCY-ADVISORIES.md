## Why Vinext requires a separate runtime assessment

The [primary Vinext README](https://github.com/cloudflare/vinext#vinext), freshly retrieved25October, describes a Vite reimplementation of the Next API surface rather than consumption of Next build output. Current upstream documentation is context, not proof about every behaviour in the pinned package. Installed exact `vinext 1.0.0-beta.5` source supplies the stronger local evidence:

- `vite.config.ts` uses Vinext/Vite/Cloudflare; `scripts/run-framework.mjs` invokes Vite/Vinext; `worker/index.ts` delegates non-domain routes to `vinext/server/fetch-handler`.
- Installed `vinext/dist/server/fetch-handler.js` delegates to a generated Vinext Worker entry; `app-server-action-execution.js` imports Vinext payload/stream/CSRF machinery. This is sufficient to reject the assumption that the Next package's Node server is necessarily the request handler, but not sufficient to certify the whole action decoding path.
- Installed `vinext/dist/server/image-optimization.js` documents Cloudflare Images or passthrough and SVG default rejection. The resolved sharp workaround independently qualifies the first Next advisory.
- Existing app-level API JSON parsing in `lib/domain-handler.ts` streams and rejects above220000 bytes. This limits those specific domain routes, not every framework route, server action, Worker message or exported SDK function.

No live unauthenticated reachability probe or server-action exploit was attempted. Preserve current private hosting; do not widen permissions to investigate.

## Zod mitigation and remaining boundaries

`lib/foundry/platform.ts` calls `assertJsonBudget` before `artefactSchema.safeParse`, per-adapter parsing or output-bundle parsing. It caps approximate bytes262144, depth18 and nodes20000; rejects sparse/extended arrays, cycles, accessors, active values and nonfinite numbers. This materially limits the collection/error amplification described by the advisory for **these guarded entrypoints**. Direct use of an exported raw schema does not inherit that guard automatically. The prewalk may itself transiently encode a large string before rejecting it, so it is not a universal constant-memory parser.

During this review root added narrowly scoped pre-Zod checks to the new Python paths:

- `admitPythonResult` independently rejects more than8 outputs, more than200 table rows, more than30 columns/cells per row, overlong stdout/stderr/error strings and oversized PNG base64 before schema traversal. These checks prevent an arbitrary Worker-result collection from relying solely on `.max()` inside Zod.
- `admitScienceManifest` independently caps requested packages6, package/assets collections40 and dependencies40 before schema parsing. Corresponding schemas now carry those maxima too.
- `loadScienceAssets` already streams and rejects manifest/controller responses above50000 bytes and assets above their declared bounded size, then verifies exact size/SHA256. The small trusted same-origin manifest path is therefore narrower than an unrestricted external upload. Direct callers of the exported validator still need its guards.

The changes were inspected in source; the final targeted test result below records execution. They **do not** prevent memory used by browser structured cloning before message admission, Python/WASM allocations, or all paths through baseline Zod. Worker timeout, iframe disposal and schema limits are complementary controls. No hard browser heap quota is claimed.
