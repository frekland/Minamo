## Executive diagnosis

**The leading failure is an incomplete and fragmented *current-work projection* combined with a Stage-first interaction hierarchy, not established canonical data loss.** Recent Notes, saved checkpoints, authored Steps, Questions, Library references and Activity evidence exist, and some explicit connections/return paths work. But the UI does not offer a coherent, provenance-aware answer to “what changed and what should I do now?” across those sources. Different components independently show authored Stage sequence, recent linked writing and the last explicit checkpoint. A newer Note can contradict an older next action without changing the older checkpoint, and the interface leaves reconciliation to the learner.

It is **not correct** to conclude that (a) all Notes are unlinked, (b) Project continuation cannot traverse a Question, (c) Library never preserves return context, (d) a new schema/vector index is already necessary, or (e) the newest prose may safely overwrite a checkpoint. The precise failures differ by path.

## End-to-end traces

### A. Project and Stage: correct facts in mutually competing surfaces

1. In the hosted **TEST ONLY** Project the overview’s revised purpose acknowledged that the original objective mood-scoring approach had been abandoned. Nevertheless the primary organisation remained authored **Steps 1–5**, with linked Questions and Resources/Project map. Its synthetic Project-root “Start first step” is **expected under test-fixture exclusion**; it is **not** evidence that live owner continuation is failing for all Projects.
2. Opening its personal-labels Stage showed a Guide, linked Question, Resources and a right-side Recent work area. Several newer linked Notes were marked **“Edited after the latest checkpoint.”** The work discussed a later v7 privacy/remember-labels direction and an unresolved manual re-test.
3. Immediately below, **“Latest saved learning”** still showed the *earlier* S03/H checkpoint and v6-oriented verification/next step. The checkpoint was dated honestly; the product nevertheless gave the learner two competing notions of “now” with no integrated answer. **Classification:** retained evidence + stale checkpoint relative to later writing + missing reconciliation, not timestamp corruption or missing Note data.
4. Source confirms the architecture: [journeyStages](../../app/journey-route.tsx) reads authored learningShape.stages (or sections); [JourneyRoute](../../app/journey-route.tsx) always offers Step N of M, Guide, Previous/Next, a separate [LearningActivity](../../app/learning-activity.tsx) and [LearningDevelopments](../../app/learning-developments.tsx). Neither a new Note nor a run changes the canonical Step sequence. The [Project map](../../app/project-map-canvas.tsx) reflects declared relationships, not a learner-adaptive working focus.
5. An older [LearningPerspective](../../lib/learning-work.ts) can be marked stale for changed/withdrawn dependency evidence; it is **not** a semantic contradiction detector for later Note prose. The truthful non-silent-update rule in [readLearningActivity](../../lib/learning-activity.ts) is a valuable safeguard, but the interface needs a way to expose the unresolved discrepancy as a decision, not merely juxtapose two feeds.

### B. Note capture → linked work: connection exists, usefulness is incomplete

- [noteCaptureLinks](../../lib/note-capture-context.ts) implicitly attaches **only the exact current reading**. A task beside a different reading is an **optional, deliberate second link**, and a task link is not silently inferred. [Workspace](../../app/workspace.tsx) passes current reading/Stage context into [NotesPanel](../../app/notes-panel.tsx); a “Note on this Article” action and contextual Note actions are genuinely implemented. A global/spontaneous Note can remain deliberately unlinked. Preserve that freedom.
- [readLearningActivity](../../lib/learning-activity.ts) gathers owner-scoped Note/Annotation/Flag/Run items if they have an **explicit matching link or reading anchor** to the exact Stage, one of at most eight related Questions, or a bounded supporting Article/Source (especially marks). A semantic mention of a Project without a link is not promoted to a relation. Default recent list is eight (max 20), bounded by scope/scan/bytes and chronology; it can be partial.
- Linked Notes appear in Recent work, with full-ish preview prose, edit-after-checkpoint markers and a source navigation link. However [ThinkingItems](../../app/learning-activity.tsx) does not make a Note’s reported **next intention, unresolved issue or revised claim** actionable in the Stage; the user must read and reconcile prose. Adding an implicit task relationship everywhere would produce false provenance and is **not** the recommended shortcut.
- **Unproven:** precise frequency of unrelated Notes in real use, whether the optional task-link control is understood/used, and whether a concrete in-task evidence interaction solves the owner’s “note remains disconnected” complaint. Those are candidate-task checks, not reasons to ask the owner to repeat the diagnosis.

### C. Project/Home/GPT continuation: a destination is not a recovery of thought

[resolveProjectContinuation](../../lib/project-context.ts) has real safeguards and useful closure: it considers eligible non-withdrawn/non-superseded Project/Question checkpoint evidence, then owner Notes explicitly linked to the Project or an associated Question, with owner rights/learning-scope/exact-record checks and bounded completeness. **It can traverse a one-hop Question association; do not report this as missing.**

But its choice is of **one** recent eligible Note newer than the checkpoint; it skips a Note resolving to more than one distinct task target, excludes unlinked Notes, and returns a destination/title/date/reference rather than a semantic reconciliation. [projectContinueChoice](../../app/journey-route.tsx) prefers that destination; otherwise the last opened Stage from sessionStorage or the first Stage. **Last opened ≠ last actually worked on.**

[homeProjectContinuations](../../lib/learning-work.ts) similarly discovers recent linked Notes and parent Projects but renders the Note-based Home card’s **shortSummary as merely “Recent Note.”** It does not tell the learner what was tried, what changed, what remains open or what to do next. Meanwhile [getLearningContext](../../lib/learning-work.ts) and [LearningDevelopments](../../app/learning-developments.tsx) derive the “Latest saved learning” account, facts, corrections and nextAction from an **explicit checkpoint**, not newer Note semantics. Correct authoring/rights safeguards are in place; the learner-facing *current* account is insufficient.

**Different GPT read path:** The direct Project-root [get_minamo_context omission recorded in V89](../acceptance/2026-11-01-v89-workbench-research-baseline.md#retrieval-finding-that-changes-the-architectural-diagnosis) occurred for Question-linked return Notes in selected synthetic examples despite relatedTruncated:false. Exact reads and Project continuation could recover them. This is a **specific direct-root context-closure blind spot**, not a statement that every Minamo context API or UI misses Question-linked Notes. Any D4 fix should specify the *particular* read contract and bounded, rights-filtered traversal.

### D. Stage → Library → Activity → return

- In the hosted Stage, Resources opened a filtered **Project resources** sheet with two relevant Articles, one directly linked to the Step and one via the associated Question, each with a reason. Opening the direct Article retained returnJourney/returnStage and rendered **Back to Step**. The Article had a section table of contents, a “Note on this Article” action and related Project/Article backlinks. These capabilities are reusable, not absent.
- In the Article examined, **Related content did not expose a relevant Activity**, while [Practice & review](../../app/practice-library.tsx) is a separate catalogue. The observed Practice list displayed Activities, a search input and display options. [practice-index](../../lib/practice-index.ts) filters Activity/Run kinds, learning-space and **title** query; it has an exact Activity filter for return/history, but no task/Stage/Article-context relevance query. A learner must already know what to look for or navigate away. This is a concrete **discovery asymmetry**, not proof that no Activity has a canonical Article link.
- [practice-return](../../lib/practice-return.ts) preserves some **Practice → linked source → Practice** journeys. The reverse “I am reading this passage in a Stage; which Activity uses it?” is not supplied by the inspected Project Article surface or Practice catalogue.
- An earlier [V89 browser detour](../acceptance/2026-11-01-v89-workbench-research-baseline.md#actual-authenticated-browser-research-independent-of-fixture-contents) showed **Question → linked Note → Article → related-Question backlink** dropped returnJourney/returnStage and lost Back to Step, even though the records themselves remained accessible. This is a demonstrable multi-hop navigation-state leak; test it as a route regression rather than assuming a global broken Back button.
- Library’s [browse state](../../app/library-browser.tsx) supports Areas/Subjects, Topics, References and search; source and D1 show discovery is catalogue/content oriented, not task-Activity oriented. Global search defects remain independently tracked in [UX register](../ux/REGISTER.md).

## Truthful return-state contract: five owner questions

The following is a **read-projection investigation contract**, not a new database schema and not permission for GPT to invent conclusions. Source categories: *saved event*, *owner-reported writing*, *observed execution/result*, *inferred*, *unknown*.

| Owner needs on return | Canonical evidence that may support it | Current selection/presentation and gap | Safe candidate read behaviour |
| --- | --- | --- | --- |
| **Last actual work** | timestamped exact Note edits, Annotations, saved Run/attempt, checkpoint, linked Question/Stage; distinguish creation/update time and actor | Stage Recent work shows linked items; Home Project Continue picks a target from recent Note/checkpoint and labels “Recent Note”; last opened Stage stored in sessionStorage is navigation only. Missing/unlinked/ambiguous work is out of scope. | Say **“last recorded linked work”** with time, author and exact source; offer alternate strands and “more may exist.” Never equate a visit, save or scripted terminal paste with completed learning. |
| **Next intended activity** | optional explicit checkpoint nextAction, owner’s later Note statement, an explicit task choice; authored next Stage is *not* necessarily personal intention | Latest saved learning may repeat a superseded-by-events nextAction; recent Note prose can contain a newer intention but is not reconciled. | Show the dated checkpoint action and any later **explicitly written** intention as potentially conflicting candidates. If no authoritative agreed intent: **unknown / confirm or choose**. No autonomous commit. |
| **Outstanding problems** | checkpoint nextQuestions, linked Question history, unresolved Note claims/attempt feedback, provenance of source | Last checkpoint “Still open” may not reflect newer resolution, addition or rewording. Question links are separately browsable; no current adjudication of issue lifecycle. | Group candidate open concerns with cited source/time and whether later writing *appears* to address them. Ambiguity remains visible for learner confirmation. |
| **Misconceptions addressed** | checkpoint facts explicitly marked misconception/correction; learner-authored correction and cited evidence; independent test receipts where applicable | Resume has Misconceptions/Corrections categories from eligible checkpoint, but later Note changes do not become a correction automatically. | Show only established **recorded corrections** as such. Distinguish “learner reported revised belief” and “seems contradicted” from a verified correction; expose supersession chain. |
| **Progress/what changed** | changed Note revisions, documented decisions and reversals, attempts/results with provenance, checkpoint change facts, source passages | Step N of M and older summaries are prominent; Recent work is verbose chronological list, not a change-focused comparison. | A short **evidence-backed change ledger**: previous position → newer work → revised/contested position → next check, each linkable; no score, false mastery, automatic completion or single mandated current concern. |

**Do not conflate these evidence types:** a user Note may contain fictional/scripted dialogue or pasted terminal output. Its actor and updatedAt do not independently verify every statement inside it. Cross-time semantic comparison is allowed as **labelled hypothesis**, not tool instruction, hidden state mutation or unquestioned truth.

## Ranked engineering probes before design commissioning

All items below are **GPT-autonomous read-only preparation** unless a separate bounded test/implementation commission is explicitly given. Work in task order, not a generic feature inventory:

1. **[P0, D1-close / D4 design input] Build a five-question return ledger from existing synthetic histories.** Extend the preliminary three-history comparison above across weekend, documentation-sceptic and interrupted sparse cases: read exact Notes/Questions/checkpoints/attempts and both direct-root/Stage-context responses. Include contradictory and no-evidence cases; label author, date, revision, link path, coverage, source and uncertainty. Deliver side-by-side *what the UI says now* versus *what evidence warrants*. Keep source excerpts brief and synthetic.
2. **[P0, regression specification] Encode the split-current-state case as a non-mutating test expectation.** In an existing fixture state, assert: newer Note visible, older checkpoint dated and still retained, no truthful current synthesis; identify the minimum read-projection contract to flag a later conflicting intention. A future fix should test correction/withdrawal, missing rights, multi-target Notes and no automatic promotion. Do not turn old Notes into checkpoints silently.
3. **[P1, route/interaction regression] Reproduce the precise multi-hop return-loss path and the working direct Back-to-Step path side by side**, including direct, Question-mediated and Activity-linked Article, retained draft, exact section/rendition and learning-space switch. Source-trace the lost context parameter. Add a test only when commissioned; do not make a blanket claim from one detour.
4. **[P1, task relevance] Inventory source-proven Article ↔ Activity/Question/Stage relations in selected sparse and non-technical examples.** Determine whether relevant Activity edges are absent in authored data, present but omitted by Project Resources/Related content, or present but not searchable from Practice; measure interaction cost without treating missing links as licence to guess them. Compare lightweight cross-reference affordance against a more structural task-first route.
5. **[P1, D2/D3 input] Contrast three structural interaction hypotheses on the same evidence:** (a) minimal contextual joins and truthful discrepancy banner; (b) a living, revisable inquiry/episode; (c) an evidence table or field notebook with user-selected context. Compare **capture-before-Project, reading-to-Activity, contradictory return, sparse/non-technical work**. Borrow prior-art mechanisms of referenced blocks, explicit supersession, source selection and adjacent evidence, not branded layouts or imported code.
6. **[Implementation gate only]** If a read-only proof cannot express the needed uncertainty without a durable user decision, prepare a **bounded schema/domain option matrix** (derived projection vs explicit user-confirmed interpretation vs migration) with rights, rollback, coverage, latency and refresh behaviour. Do not preselect a generated authoritative “current state,” vector search or Project rewrite.

### Why this is not yet a design commission

- **GPT can do next:** precise synthetic read comparisons, source/route debugging, tests specified but not run against mutated state, D2 prior-art interaction teardown and D3 divergent task storyboards/proposals. This report’s source/browser mechanism trace and the preliminary three-history MCP cross-check are complete enough to guide that work.
- **Only the owner can determine:** whether a revised Project entry genuinely reduces friction, which two conflicting pieces of evidence deserve foregrounding during real use, whether a candidate feels adaptive rather than intrusive, which one design to build, and permissions for real data, new external services, mutations, migrations or Site release.
- **Still unproven:** full native Site/public-main code identity; an end-to-end persisted new Note→Activity→cold GPT return trace in this research; all-corpus Article/Activity coverage; natural-use findability; responsive/keyboard/assistive acceptance; rights/latency of any expanded closure; nine independent authenticated GPT contexts. Keep the [V89 technical gate](../acceptance/2026-11-01-v89-workbench-research-baseline.md) separate from D1–D3 discovery.

**Handoff rule:** Start the next Minamo design chat from this diagnosis and the owner’s first-hand priorities, not the superseded Work/Questions/Evolution or fixed A/B contracts. First test a *truthful joined return* and contextual Activity path on exact synthetic evidence; then bring genuinely distinct, low-cost interactions for owner judgment. **No UI/schema/fixture/deployment change was made or authorised by this audit.**
