**Static behaviour established from source:**

- v5 holds selected mood, track data and input label in React state. The track state is owned above filtered cards; mood switching can preserve a label, but reload initializes the catalogue anew. There is no Web Storage read/write in v5.
- v6 obtains localStorage via browserStorage, lazily initializes tracks from readSavedLabels/applySavedLabels, writes through saveLabels on adding a personal label, and offers a Clear stored labels button. Its helper parses JSON, validates saved entries and catches storage/parse exceptions.
- v6 **does not require explicit opt-in** before writing personal labels despite the helper defining consent functions; the helper's success booleans are ignored by UI. With inaccessible/null storage, optional-chained operations can also return apparent success from the helper, and a clear action resets React state even if durable removal fails.
- v6 calls saveLabels **inside a setTracks functional state updater**, a side effect in a location React expects to be pure. This merits source-level analysis for repeated updater evaluation and state/storage divergence, but no runtime defect was observed.

If no actual browser execution is available, keep this explicitly as a proposal.
