**Static expected v7 state transitions:**
1. No consent key: remember false, initial TRACKS in memory, no restoration. On mount a cleanup effect tries to remove the saved-label key. This prevents normal migration of v6's implicit saving into v7 without opt-in, provided storage calls succeed.
2. Consent enabled: setRemember(true), setConsent(storage,true), then saveLabels(storage,tracks). Later label additions write localStorage when remember is true.
3. Consent disabled: setRemember(false), remove consent and saved-label keys; **does not reset the current mounted tracks**, so visible labels can remain until reload. This differs from the separate Clear all button, which resets tracks immediately.
4. Refresh: if consent persisted, read stored labels; otherwise use fresh TRACKS.
5. Missing, blocked or throwing storage: readConsent falls back to false, readSavedLabels to an empty object. **setConsent/saveLabels/clearSavedLabels can incorrectly return true on null storage** due to optional chaining. Exceptions are swallowed into false values; v7 ignores returns and provides no error message.
6. Shared profile: successful localStorage is same-origin/profile scoped and potentially readable by another user of that browser profile. A separate tab, stale in-memory state, site data clearing, restored availability and storage failures need distinct experiments.

Potential helper failures should not be upgraded to observed runtime defects. The UI checkbox can represent local React state even if the consent write failed; the Clear all control can clear React memory while failing to remove browser storage. ## 12. Stable findings: severity, provenance and recommendations

### M2M-S05-IR-001 — Storage helper false-positive success without storage
- **Severity / confidence / reproducibility:** Medium / P2 source defect candidate; High; Deterministic from static JS semantics; no independent browser reproduction.
- **Exact evidence:** Pinned label-storage.mjs functions setConsent, saveLabels, clearSavedLabels, and browserStorage.
- **Directly observed:** Optional call storage?.setItem/removeItem performs no write for null storage but control falls through to return true; readConsent(null) is false.
- **Inference / remaining uncertainty:** Actual native browser handling, private-mode failures and user-visible symptom untested.
- **Affected functionality and possible user impact:** Persist/consent/delete operations may be silently reported as successful when no storage exists.
- **Recommended action:** Guard missing storage explicitly; add null, throwing getter, quota and remove-failure tests; surface meaningful status to caller.


### M2M-S05-IR-002 — Consent checkbox and clear controls can diverge from durable storage
- **Severity / confidence / reproducibility:** Medium / P2 design/defect candidate; Medium-high; Source-level inference only; no observed real-browser failure.
- **Exact evidence:** Pinned v7.jsx changeRemember/add/clear handlers and helper return values.
- **Directly observed:** React remember state is set regardless of storage success; clear resets tracks regardless of removal; errors are not rendered.
- **Inference / remaining uncertainty:** A storage-denied path could show “remember” checked though not persisted or “clear” visually complete while a key remains inaccessible. No runtime proof.
- **Affected functionality and possible user impact:** Privacy-sensitive opt-in/opt-out trust and recovery after storage access returns.
- **Recommended action:** Define success/failure UX and retry/verification policy; explicitly differentiate temporary state, stored key and user consent; test failure paths.


### M2M-S05-IR-003 — Opt-out removes durable saving but not in-memory labels
- **Severity / confidence / reproducibility:** Low / P3 design decision; High; Static implementation directly visible; browser effect not independently observed.
- **Exact evidence:** Pinned v7.jsx changeRemember(false) versus “Clear all my labels”.
- **Directly observed:** Unchecking attempts to remove saved keys but leaves tracks state untouched; Clear all setsTracks(TRACKS).
- **Inference / remaining uncertainty:** May be intentional and consistent with “stop remembering” as distinct from “erase now”.
- **Affected functionality and possible user impact:** Shared-device users may expect immediate disappearance when disabling remembrance.
- **Recommended action:** Teach/check exact current-tab versus refresh semantics; label and differentiate the controls; decide policy before code changes.


### M2M-S05-IR-004 — Existing browser test covers normal v7 path, not storage error paths
- **Severity / confidence / reproducibility:** Medium / P2 evidence gap; High; Test source independently read; no tests executed during this review.
- **Exact evidence:** Pinned revisions.test.mjs (four Node tests) and browser.test.mjs (single Playwright/Vite test).
- **Directly observed:** Browser test contains opt-in/reload, opt-out/reload and v6→v7 no-implicit-restore assertions; Node uses Map-backed fake storage.
- **Inference / remaining uncertainty:** Presence does not prove an actual passing run, running source identity or denial/quota failure handling; PR #29 under-described this separate browser test.
- **Affected functionality and possible user impact:** Risk of both undercounting available tests and overclaiming runtime acceptance.
- **Recommended action:** Record test-inventory tiers and capture checkout, command, full output, exit status, time; add denial/throwing-storage and visual feedback checks.

### M2M-S05-IR-006 — Controller and general operation receipt namespace is easy to confuse
- **Severity / confidence / reproducibility:** Low / P3 integration/contract; High; Reproduced with canonical read-only calls.
