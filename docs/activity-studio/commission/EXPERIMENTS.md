## Nontrivial challenges to investigate autonomously

- A “bug museum” of small reviewed failure specimens across Python, networking, SQL, React, statistics and Japanese; each can be reused with fresh safe variants rather than duplicating a full Journey.
- A “prediction notebook” of parameterized experiments where the learner chooses input, states an expectation, examines actual results and keeps a **short** linked Note with provenance.
- A “counterexample generator” that challenges false assumptions by constructing a minimal failing case, with deterministic shrinking and independently verified reference.
- A “Git time machine” showing synthetically verified commit-by-commit product development, tied to a local repository and actual tests.
- An “algorithm composer” in React Flow / Konva where learner builds steps in a visual graph and exports a real corresponding Python/JS scaffold; verify semantic correspondence.
- A “scientific detective board” mixing Plot, math, source data, controlled sliders and actual tested analysis.
- A “music coding studio” with note sequencer, playable Tone.js patterns and generated-but-external Strudel code, reversible pattern/time traces.
- A “Japanese etymology/grammar atlas” with ruby compounds and authored morphology relationships, without claiming unverified AI readings.
- A “learning project studio” that can create a small scoped GitHub template from an Investigation and retain exact local startup pathways.
- A “lesson translator” that takes a verified exercise template and adapts modality/language/complexity while preserving test oracles, accessibility and solver feasibility.

## Test evidence and status rules

Every experiment must have: branch/immutable commit, source/bundle hash, exact command, actual exit code/output/screenshot, interpretation, thrown errors, mobile/desktop environment, test and dependency versions, independent oracle or negative case, source permissions, impact on current learning Notes/MCP, and support/migration/rollback requirements.

Conformance classes:
1. source/research only;
2. tests/runnable fixture;
3. actual isolated Worker/real browser;
4. integrated local synthetic D1/MCP and current rich Note/Reader;
5. owner-private hosted authenticated acceptance;
6. physical Android/assistive user acceptance.

A green unit suite does not substitute for a higher class; failure to verify must be stated. Do not report “published” simply because a draft PR exists.

## Definition of useful completion

A substantial bank of **actual working integrated dormant activities**, realistic local GitHub round-trips, one or more fully used Atlas lenses, adversarial tests, source/recovery compliance and precise Sol Light activation packages. Number of prototypes is not capped: continue across domains until actual task/tool constraints or poor marginal value. Report what was not implemented, including runtime boundaries that require stronger future work.
