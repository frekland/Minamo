# Focused product and learning-quality challenge

**23 October 2026 · design investigation only · V21 baseline.** This challenges the [selected implementation plan](IMPLEMENTABLE-PLAN.md), including its decisions to reuse existing tutor reads, Area hubs and rich Notes. The original explorations are context, not a cumulative backlog. The justified changes below have been reconciled into the selected plan's architecture, slices and acceptance criteria. No proposed production feature was implemented, merged or deployed; no genuine learner record was edited.

## Assessment and dispositions

The three integrated outcomes remain the right scope. The challenge strengthens continuity semantics and personal rediscovery, and makes coherent rich-content interaction and optional active self-study explicit. It does not add another product architecture.

## Continuity experiments and tutoring assessment

[Reproducible fixture](spikes/continuity-challenge.mjs) compiles the actual current domain handler with the repository's isolated Miniflare D1/R2 test fixture. It exercises HTTP and local MCP, including omitted profile selecting tutor. All principals, records and thoughts are synthetic; fixture storage is disposed in `finally`. Add `--contexts /absolute/output.json` to emit synthetic response bodies for another independent assessment; default execution prints metrics only. [Metrics](spikes/continuity-challenge-results.json) are UTF-8 JSON sizes, not model tokens or hosted latency.

```sh
node docs/future-learning-review/spikes/continuity-challenge.mjs --checkout /absolute/minamo-v2-checkout
node docs/future-learning-review/spikes/growth-challenge.mjs /absolute/minamo-v2-checkout
```

| Earlier provisional choice, then six narrow reported attempts | Tutor 4,399 bytes; full 11,598; tutor limit 8 = 5,666 and recovers earlier reason | Default economy is useful, but absence is not revocation or proof no earlier reasoning exists. A necessary extra read can be worthwhile |
| Existing dependency-checked perspective | Full includes the optional authored account; tutor omits it despite computing eligibility. Correction/withdrawal of its dependency yields stale status and empty prose | Expose this existing optional orientation in initial tutor, with exact dependency/status semantics; compare it with newer work rather than declaring it automatically current |
| Page backwards | Page 2 = 4,346 bytes; `resume` becomes c2 although latest is c6; no page-role field | Remove historical-page ambiguity server-side; do not require every GPT/client to guess from previous responses |
| Correct earlier interpretation, no new practical next action | Corrected c0 becomes resume by revision time, no nextAction; latest reported attempt/action remains in priors | Expose chronology/selection basis. Correction is not automatically new progress or a direction to rewind |
| Withdraw that correction | Tutor excludes it; full history retains withdrawn stub; stored revisions preserved | Preserve current eligibility and invalidation. Persistence is not permission to serve withdrawn wording as current |
| Excessive checkpoint detail | 17,568-byte request; tutor 21,807; full 47,068; all 12 repeated attempt facts and decisive correction returned | Improve what GPT saves; do not select the first N facts and lose the constraint. Canonical part budgets do not solve fact-prose volume |

A separate specialist was given the pre-perspective variant of the synthetic responses before the other research notes. The later perspective extension was checked in the same local fixture, not included in that tutoring simulation. This was an independent agent tutoring simulation, **not an installed ChatGPT fresh-conversation test**. It correctly distinguished learner reports from observed execution and proposed a small prediction/inspection step. It also identified that history-page resume could rewind work, and that the corrected earlier choice did not supply a new practical action. With wider history it recovered why remote audio-feature work had been set aside; with the verbose response it retained the decisive local-only constraint but noted repeated reports were not achievements. These observations support the response-contract changes; they do not measure learning gains or guarantee future model behaviour.

The fictional external-provider limitation is about evidence and access, not a claim about current Spotify rules. The general scenario is a learner building a project, discovering that a planned dependency is unavailable or unsupported, choosing a useful narrower experiment, and returning after several conversations. A second acceptance scenario uses a local parser/toolchain limitation so the design does not depend on music or one API.

### Server versus GPT responsibility

Server work is identity, current eligibility, exact revision/evidence resolution, explicit chronology/page roles, safe projections, bounded candidate retrieval and truthful omissions. Existing saved perspective dependencies can supply compact authored orientation; stale text must stay withheld. Valid dependencies alone do not establish semantic currency after later contradictory work, so the authored account remains labelled and GPT compares it with newer evidence. Server assembly must not decide which hypothesis is true, rewrite an abandoned direction into policy, infer mastery or compress a learner's reasoning into an invented conclusion.

GPT chooses relevant detail, explains mechanisms, checks surprising constraints against appropriate current sources, adapts scaffolding and judges whether a previous practical plan remains useful. It can ask for one prediction or discriminating experiment without producing the finished solution. A returning learner's new question can warrant revising the plan; preserving continuity does not mean mechanically obeying every historical next action. Saving remains a separate explicit request, with a concise meaningful account rather than a transcript or mandatory template.

## Frontend validation: rich content, not only cards

Production V21 Library UI was inspected read-only: the selected subject renders a title, generic subject introduction, a dense row of eight facets, article summaries and repeated subject labels; Notes remains a persistent entry. This supports the selected hub/hierarchy work. It is not evidence that every screen is defective, nor a reason to discard the current charcoal/blue system or working rich Reader.

The existing [local prototype](spikes/ui/public/app.js) was extended with longer prose, two code examples, a comparison table, a labelled original SVG trace, troubleshooting and a small prediction/worked-explanation/variation. It calls no Minamo API and supplies no observed learner result. Native HTML disclosure tests an interaction possibility; it is not a new production manuscript feature.

At a 390 px desktop container, enlarged text, contained code/table overflow and preserved synthetic writing were inspected. The first rich run exposed the writing status below its scrollport (status bottom about 976 px; pane bottom 920 px). A prototype-only feedback-row correction placed status at about 904 px inside a pane ending at 920 px, with a visible textarea about 95 px high and reading region about 410 px high. Settings close returned focus and retained the synthetic draft; opening the explanation recorded no attempt. The diagram's small-view labels also reinforce the need for readable alternatives/enlargement rather than shrinking every visual to fit a preview.

The prototype's displayed JavaScript predictions were separately checked in Node: the logging-only function returns undefined, and the branch-only function returns undefined for zero and the stated string for a positive input. These development checks are not saved learner evidence.

These are prototype findings, not production defects or phone acceptance. The prototype's research header and textarea differ from the real shell and ProseMirror/CodeMirror editors. It does not prove canonical selection, server acknowledgement, keyboard occlusion, Android Back, TalkBack, IME composition, pinch zoom or physical touch behaviour. Those remain integrated acceptance, with honest limits if no physical device is available. Do not report a narrow desktop container as Android verification.

Primary technical guidance: [MDN VisualViewport](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport) distinguishes visual/layout viewports and on-screen-keyboard effects; [W3C target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) explains minimum target sizing/spacing and exceptions. Existing plan evidence covers focus not obscured and React state ownership. These inform implementation checks, not a compliance claim.

## Library growth and independent learning

The [growth diagnostic](spikes/growth-challenge.mjs) bundles actual `workRows`, uses 100 original synthetic Notes and removes its temporary bundle. It is a pure-function/source demonstration, not a hosted query benchmark. The existing UI already labels its advanced filters as applying to loaded results; the problem is incomplete convenience at scale, not an undisclosed promise of server-wide filtering. A complete personal query path is necessary before a contextual My work view can be trusted months later.

Keep canonical Articles, evolving personal Notes, exact historical captures and explicitly saved learning reasoning distinguishable. Link them purposefully; do not merge their authority. An Article revision need not rewrite a Note, and an old captured edition must not jump to a same-named current paragraph. Member pagination and reference destinations need tests beyond a small demonstration corpus. Current source mapping, catalogue CAS and recovery remain the base.

For active self-study, [IES's practice guide](https://ies.ed.gov/ncee/wwc/practiceguide/1) rates worked-example/problem-solving interleaving as moderate evidence, explanatory questions and retrieval through re-exposure as strong, and prequestions as minimal. This supports a proportionate authored trial, not a claim of proven effects for Minamo or adult programming with GPT. Keep useful explanation accessible immediately for learners who choose it. Avoid turning every reference into an exercise; concise factual lookup is valuable too.

## End-to-end acceptance for the selected scope

1. **Return after a changed constraint.** In three synthetic conversations choose a provisional project direction with reason, encounter an unexpected provider/toolchain limit, and perform several small attempts. A fresh GPT gets the current exact task and latest saved state, retrieves earlier rationale only when needed, avoids restarting the abandoned path and proposes a useful discriminating next experiment. Repeat with seven checkpoints, a valid/stale saved perspective and no perspective; then move to a stable next Journey stage and explicitly related Investigation. Recover only relevant saved context, with no blanket Journey-wide membership, duplicated checkpoints or mandatory new Investigation. Measure meaningful retention, response size, necessary reads and learner effort together.
2. **Correct without rewinding.** Correct an older interpretation without supplying a new action; then read older pages and exact Development detail, withdraw a checkpoint and revoke a linked Source. Current versus historical roles/chronology remain explicit; no page-local resume replaces current work, no stale perspective/quote leaks, no withdrawn direction is revived. Changed canonical route and saved learning remain distinct.
3. **Large subject and old thought.** Use hundreds of Articles and personal records across subjects, with matches beyond the first page. Curated groups remain small; full membership is complete. Find an old direct/captured/accepted-parent-linked Note through a server context query and a permitted quoted phrase without manually loading unrelated work. Revocation removes quote-based hits while preserving independent prose. Check bounded row work, stable eligible pagination and truthful continuation/empty states.
4. **Deepen and reuse.** A normal GPT request finds existing useful coverage, reads its current canonical sections and improves a genuine gap instead of duplicating the resource. A second project reuses it. A catalogue-only edit leaves reading identity unchanged; a canonical correction preserves retained source/capture identity. Removed indexed parts receive explicit valid retargeting or actionable rejection, never title-based guessing. Concurrent revisions remain guarded.
5. **Use a coherent workspace.** Home → Journey/Investigation → reference → own Note → exact reading → return, at desktop and Android-sized layouts with substantial content. Preserve history/filter/position, explicit Note target, drafts and editor ownership; show slow/error/no-answer states honestly. Exact Flag/Annotation and recovery stay discoverable. Actual physical Android checks must separately cover keyboard, touch selection, Back, zoom, rotation and assistive focus; prototype evidence cannot discharge them.
6. **Learn independently by choice.** Read a mechanism, optionally predict, compare an authored explanation or actual local output, inspect a failure and vary the example. Save a reflection only if wanted. No compulsory response, session, quiz, inferred mastery or progress write occurs; a later GPT sees only explicitly saved reasoning. Benchmark the educational substance independently of publication success.
7. **Economy without erasing reasoning.** Compare verbose and concise checkpoints for the same scenario. The fresh tutor retains the decisive limitation, evidence basis, current uncertainty and useful next action. If details are deferred, exact IDs/revisions/roles and a usable focused read are provided. No truncation is passed off as a complete account; necessary extra retrieval is preferable to an unsupported teaching direction.

## Remaining risks and readiness

The design is ready for an autonomous implementation commission in the selected scope. New work is bounded inside slices B–D; continuity semantics should be corrected before the complete return-to-GPT story is judged. Article FTS remains conditional and does not block complete personal discovery, useful authoring or the workspace improvements. No new durable learning family or cloud preference schema is required.

Material implementation risks are rights-aware personal quotation matching/pagination, consumer compatibility for historical responses, perspective invalidation under current eligibility, and real editor/focus/keyboard integration. Current experiments do not establish hosted latency/row work, physical Android behaviour or actual installed ChatGPT tutoring transfer. Those are concrete validation gates, not reasons to reopen the entire product investigation. Free existing infrastructure remains the constraint; direct connectors, extra runtimes, offline packs, taxonomy growth, automatic maintenance and generic reveal widgets remain deferred or rejected as stated in the selected plan.
